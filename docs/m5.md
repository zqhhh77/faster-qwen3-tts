# M5 CPU 后端

每次部署选择一个后端。M5 使用独立 Python gRPC 服务，Qwen 继续使用原有 HTTP/SSE 后端；本次不重新构建 Qwen 镜像。对外 HTTP 路由、字段、音色列表格式、PCM/SSE 协议及磁盘缓存语义保持一致。

## 运行结构

```text
客户端 → Go HTTP → 磁盘缓存/共享任务 → engine.Backend
                                        ├─ qwen3：原有 HTTP/SSE
                                        └─ m5：gRPC → ONNX Runtime CPU
```

`internal/engine/backend.go` 定义后端能力，`m5.go` 负责 gRPC；`proto/inference.proto` 是协议源。Python `backend/m5/server.py` 处理 RPC，`runtime.py` 加载模型、校验资产、预热参考音色和生成音频。必要的上游源码固定在 `backend/m5/vendor`，版本见该目录的 `UPSTREAM.md`；构建不依赖本机 `third_party` 目录，也不会拉取上游 main。

`M5_WORKERS=N` 创建 N 个独立模型实例，每个实例持有独立 ONNX sessions、解码状态和已预加载的音色编码。一次请求独占一个实例，结束或取消后归还；元数据 RPC 可以在生成期间执行。Go 推理并发与实例数保持一致，额外请求在 Go 的有界队列等待。Compose 默认 N=2，独立启动 Python 服务时默认 N=1。实例数可配置为 1～32，实际并发能力取决于 CPU 和内存。相同请求共享生成，不增加推理槽位。任务 deadline 包含排队时间；单个甚至全部 HTTP 读者断开都不会改变已有的共享任务策略，超时/网关退出才取消任务。Python 在音频块之间响应取消，ONNX 正在执行的原生调用不会被强制中断。

推理端将 float32 分块限幅转换为 24 kHz/mono/s16le。gRPC 直接发送 bytes，无 Base64/WAV 包装；只有模型 EOS、非空音频、样本计数匹配、显式 done 和最终 gRPC OK 都满足，Go 才提交缓存。截断、异常和取消不提交成功缓存。

## 模型与音色

原始 FP32 模型放在仓库根目录下的以下位置。

```text
models/M5-TTS-50M-ONNX
```

容器挂载到 `/models/m5`，权重不打进镜像。启动根据 `checksums.json` 校验所有上游要求的资产，JSON 允许仅有 Windows CRLF 与 LF 换行差异，其他内容差异仍失败。不会修改原始模型文件。

### CPU 双路流式合成

在仓库根目录执行一次离线转换。目标使用新目录，转换器校验源文件，仅量化 `depth_frame.onnx` 的常量矩阵乘法，并校验生成的模型包。首次安装转换工具需要联网。

```powershell
uv run --frozen --with 'onnx==1.20.1' --with 'ml-dtypes==0.5.4' python -m backend.m5.prepare_int8 models/M5-TTS-50M-ONNX models/M5-TTS-50M-ONNX-depth-int8
```

M5 的 Compose 默认使用以下配置。首次部署可直接使用 `.env.m5.example`。已有 `.env.m5` 的部署将这三项更新为以下值，其余配置按现场需要保留。

```dotenv
M5_MODEL_HOST_DIR=./models/M5-TTS-50M-ONNX-depth-int8
M5_WORKERS=2
M5_THREADS=3
```

服务按模型清单启用 INT8 流式路径。每个实例启动时为每个音色预先解码参考录音末尾最多 8 帧。请求到达后按所选音色恢复状态，生成 6 帧后发送第一块约 380 ms 的正文，随后每 4 帧解码一块，同时生成下一块。客户端沿用原有音色和播放速率。量化会影响音频 token 的采样，同一文本在两种模型下合成的时长可能不同。双路连续播放取决于 CPU 算力和客户端实际收包间隔。

在 i5-12400F（6 核 12 线程）上，两种不同参考音色同时请求，测试覆盖 45～161 字的 18 条告警。按网关 HTTP 客户端收到第一块正文即开始原速播放计算，首块耗时 0.52～0.74 秒，18 条均未出现缓冲耗尽。该测量覆盖推理、gRPC 和本地 HTTP 收包，现场 H5 的网络和播放调度需要在部署环境验收。

### 可选的 INT8 投影查表

如果已有 `depth_frame_precision=int8` 的模型，可离线预计算深度解码器 14 个码本阶段的首层 Q/K/V 投影。每个表按上一个音频 token 索引，所有动态正文和音色都可以共用。请在与部署端相同的 CPU 架构和 ONNX Runtime 版本上准备。以下命令生成一个新的完整模型目录，支持继续使用原目录进行对照或回退。

```bash
uv run --frozen --with 'onnx==1.20.1' --with 'ml-dtypes==0.5.4' python -m backend.m5.prepare_int8 --depth-lut models/M5-TTS-50M-ONNX-depth-int8 models/M5-TTS-50M-ONNX-depth-lut
```

转换会校验源文件、逐项比对 16 组输入的输出 token 和下一帧隐状态，再写入新模型校验和。新目录约 1.71 GiB，其中查表比原 INT8 模型多约 84 MiB。使用原有调优脚本比较两份模型，保持正文、音色、并发和线程数相同。部署时将 `M5_MODEL_HOST_DIR` 指向选定的目录并重建容器。

在本地限制 8 个逻辑 CPU、两实例各 4 线程的交替对照中，两条动态告警全部完成的平均耗时由 12.35 秒降到 12.05 秒。两轮中累计断流由 3.53 秒降到 2.43 秒，仍有播放中断。双实例在独立进程树测试中的峰值内存分别约为 2513 MiB 和 2681 MiB。目标机器可用以下命令测试首块即播的连续性。

```bash
python -m backend.m5.tune --model models/M5-TTS-50M-ONNX-depth-lut --concurrency 2 --workers 2 --threads 4 --texts alerts.txt --rounds 3 --require-continuous
```

### 加快流式音频解码

从现有 INT8 权重生成同时带投影查表和快速音频解码器的模型目录。

```bash
uv run --frozen --with 'onnx==1.20.1' --with 'ml-dtypes==0.5.4' python -m backend.m5.prepare_int8 \
  --depth-lut --fast-codec models/M5-TTS-50M-ONNX-depth-int8 models/M5-TTS-50M-ONNX-fast
```

如果源目录已经做过投影查表，只传 `--fast-codec`。转换器把流式解码器中的 25 个稠密卷积改为混合精度运算，将权重按输出通道量化，保留原有分块大小、推理语速和音色选择。转换结束前会对参考录音做流式解码，检查每块长度和数值，并要求新旧波形的信噪比达到 20 dB。合成的音频 token 相同，量化后的 PCM 波形会有差异。

本机限用 8 个逻辑 CPU，两个实例各 4 线程，同一对动态告警预热后交替对照 3 轮。以投影查表版为基线，同时提交的两条告警平均完成耗时从 12.03 秒降到 9.34 秒。gRPC 客户端从首块起播，基线 6 条请求累计等待补音 3.68 秒，快速解码版 6 条均未耗尽缓冲。两组使用相同的 6 帧首块、4 帧后续块设置。快速版整包约 1.63 GiB。

在相同 CPU 配置下，另用 Go HTTP 网关测试 6 条不同的动态告警（23～143 字）。两个版本各自从空缓存开始，每次同时提交两条，各用一种参考音色。按客户端收到首块正文即以原速播放计算，基线有 4 条耗尽播放缓冲，快速版 6 条均连续供音，首块在 0.578～0.656 秒到达。最长一条生成了同样的 34.22 秒语音，完成耗时从 33.45 秒降至 25.58 秒。6 对 WAV 的采样数逐一相同，新旧波形的信噪比为 27.51～29.45 dB。

在目标 CPU 上用同一对正文分别测试两份模型，再用现场常用音色试听。切换时，将 `.env.m5` 中的 `M5_MODEL_HOST_DIR` 指向新目录，执行以下命令重新创建推理容器。网关沿用现有镜像，客户端继续通过 `voice` 选择音色。

```bash
docker compose --env-file .env.m5 -f compose.m5.yaml up -d --no-deps --no-build m5-backend
```

### 通用正文的末级上采样优化

已经使用投影查表和快速解码的模型，可继续生成一个改写最后两层音频上采样的独立目录。该转换把步幅为 4 和 3 的转置卷积权重按输出采样位置离线排列，运行时使用 FP32 矩阵乘法。它适用于所有正文，不依赖告警模板或字段缓存。

```bash
uv run --frozen --with 'onnx==1.20.1' --with 'ml-dtypes==0.5.4' python -m backend.m5.prepare_int8 \
  --fast-upsampling models/M5-TTS-50M-ONNX-fast models/M5-TTS-50M-ONNX-fast-upsample
```

转换结束会用参考录音验证流式分块、输出长度和波形误差。新模型通过 `manifest.json` 中的 `codec_upsampling_layout=phase_fp32_last_two` 标记。它保留音频 token、采样率、语速、音色接口和分块设置，PCM 会因浮点运算顺序变化。

本机限制 8 个逻辑 CPU，两个实例各 2 线程，关闭告警模板和动态字段缓存，用两种音色同时生成 6 条首次出现的普通中文正文。交替复测中，两条请求全部完成的平均耗时从 6.171 秒降到 5.996 秒，首块平均从 0.666 秒降到 0.646 秒。6 对 PCM 的信噪比为 38.23～42.32 dB，参考录音的转换自检为 37.25 dB。模型包约 1.63 GiB。海光 CPU 需使用相同正文分别挂载两份模型，以 `stall_s` 和 `batch_mean_s` 决定是否切换。

### 船舶告警固定短语

当前版本默认启用 `M5_ALERT_PHRASES=on`。服务首次启动时为每个音色各生成一次“发现”“触发”“请立即关注”“请保持关注”，保存到磁盘，全部推理实例共享。后续启动从磁盘复用已有片段，只补生成缺失或损坏的片段。每个音色都会打印“告警短语预生成完成”日志，`disk_hits=4 generated=0` 表示四段全部从磁盘复用；所有音色准备好后才接收请求。请求继续传完整中文正文和 `voice`。该选项可与快速解码模型一起使用，也可在现有 INT8 模型上启用。使用当前源码和 Compose 配置构建时，以下命令更新后端：

```bash
docker compose --env-file .env.m5 -f compose.m5.yaml up -d --no-deps --build m5-backend
```

以下两条正文都会命中模板。

- `发现海巡零一，在东航道，触发超速告警，请立即关注。`
- `发现苏港二号，，触发偏航告警，请保持关注。`

匹配时，按“发现 → 船名 → 可选区域 → 触发 → 告警类型 → 关注结语”拼接。船名、区域、类型分别合成，各自按音色缓存；更换船名仍能复用原区域。区域为空时，船名后一个或两个逗号都可以。后端将缓存的“发现”和船名开头合成首包，积累到 0.8 秒可播正文或船名段结束时立即发送，后续分块继续流式发送。拼接时裁掉片段首尾多余的低音量部分，段内停顿保留。请求只包含任一关注结语时，直接读取对应音色的缓存音频。其他正文沿用整句合成。设为 `off` 可恢复全部使用整句合成。

### 复用已播报的船名、区域和告警类型

固定短语以外的字段默认实时推理。需要复用动态字段时，在 `.env.m5` 配置：

```dotenv
M5_ALERT_PHRASES=on
M5_ALERT_FIELD_CACHE_MB=256
M5_ALERT_CACHE_HOST_DIR=./cache/m5-alerts
```

Compose 将宿主机目录挂载到后端的 `/cache/m5-alerts`。直接运行 Python 时，用 `M5_ALERT_CACHE_DIR` 指定目录，默认 `cache/m5-alerts`。`phrases/` 保存固定短语，`fields/` 保存船名、区域和告警类型；文件包含生成帧数、校验和及 24 kHz 单声道 16 位 PCM。音频按需读盘，内存只保留文件索引和当前请求正在使用的片段，不预加载整个音频缓存。容器重建后仍复用挂载目录中的文件。

`M5_ALERT_FIELD_CACHE_MB` 现在限制动态字段的**磁盘文件总大小**，默认 0；0 只关闭动态字段缓存，四个固定短语仍会落盘。动态字段只在完整生成后原子写入，异常、截断和中途取消不会缓存未完成片段。达到容量后按最近访问顺序淘汰，重启时沿用磁盘记录的访问顺序。64 MiB 约可容纳 23 分钟 PCM。固定短语不占动态字段配额，旧模型或旧音色留下的固定短语文件可在停服时清理 `phrases/`，下次启动会重新生成。

缓存按音色名、参考录音内容、参考转写、模型资产、推理设置和适配源码区分。修改一个音色后，该音色重新生成，其他音色仍可复用；不同音色不会串用片段。同一音色换船时，只要区域和类型相同，就能直接复用两者。日志 `告警字段磁盘缓存命中 voice=... field=...` 可确认命中。首次出现的字段仍需推理，拆分后的片段衔接请用实际参考音色试听。每个部署使用独立缓存目录；同一后端进程内的全部 worker 共享文件索引和锁。

模型调优脚本会为测试子进程关闭动态字段缓存，以便用相同文本多轮测量 CPU 的实际推理速度。

更改 `M5_WORKERS` 时，同时重新创建 `m5-backend` 和 `gateway` 容器，使网关并发数与后端声明一致。网关可以沿用原镜像。

### 参考音色

默认附带上游演示参考录音，音色名 `default`。自定义时在宿主机建立 `references/m5/voices.json`：

```json
{
  "xiaoli": {"wav": "xiaoli.wav", "text": "与参考音频逐字一致的转写。"},
  "xiaowang": {"wav": "xiaowang.wav", "text": "另一段参考音频的准确转写。"}
}
```

参考录音相对 `voices.json` 定位；容器也可使用 `/references/...` 绝对路径。音色名允许字母、数字、下划线和连字符，最多 128 字符，配置 1～64 个音色。模型在启动时加载并预编码全部参考录音，有效默认音色必须存在。更新配置或参考录音后重启 M5 服务，再查询音色列表。

```dotenv
M5_VOICES_FILE=/references/m5/voices.json
M5_DEFAULT_VOICE=xiaoli
```

`GET /v1/audio/voices` 返回当前加载的音色及 default 标记。合成的 `voice` 可指定名称；省略/null 使用默认音色，空字符串仍为 400，不存在为 404。实际音色在计算缓存键前解析，因此省略 voice 和显式指定默认音色共享缓存。

M5 不额外设置 500 字符限制，沿用现有 HTTP 1～2048 字符校验。模型另有 token/参考音频帧/生成帧共享的上下文容量限制，不能将 2048 字符理解为任意文本都一定能生成。默认生成预算上限 `M5_MAX_FRAMES=1024`，每帧 80 ms；实际预算取配置与可用上下文的较小值。模板播报也按整条告警计算预算，包含固定短语。预算耗尽时请求失败。

语言支持 Chinese、English、German、French、Japanese、Korean；speed 仅 1，非空 instruct 返回 400。第一版不增加外部模型选择、上传音色或生成参数接口。

默认关闭 WeText 文本归一化，与示例缺依赖时的透传行为一致，数字/英文读法可能受影响。明确通过 `M5_TEXT_NORMALIZATION=off` 固定；本地需要启用时先 `uv sync --extra normalization` 再设置为 `on`（pynini/OpenFst 的平台支持需确认）。标准 CPU 镜像未安装这一可选组。归一化方式、依赖版本、模型资产、参考录音/转写、生成参数及适配源码都参与模型身份，变更后不会复用旧身份缓存。

## Windows 本地运行

仓库根目录执行：

```powershell
uv sync --frozen
$env:M5_MODEL = "$PWD\models\M5-TTS-50M-ONNX-depth-int8"
$env:M5_LISTEN = '127.0.0.1:50051'
$env:M5_WORKERS = '2'
$env:M5_THREADS = '3'
uv run --frozen python -m backend.m5.server
```

另一个终端启动 Go 网关：

```powershell
$env:TTS_BACKEND_TYPE = 'm5'
$env:TTS_BACKEND_GRPC_ADDR = '127.0.0.1:50051'
$env:TTS_MAX_CONCURRENT_TASKS = '2'
$env:TTS_CACHE_DIR = "$PWD\cache\audio"
go run ./cmd/gateway
```

本地使用 uv 管理的 Python 3.11 和 `uv.lock`。首次安装需要联网，模型只从指定的本地目录读取。Windows 可以验证网关和流式链路；镜像部署平台为 Linux/amd64，目录 fsync 在 Linux 执行，Windows 不支持该操作。

`M5_THREADS` 设置每个实例的 ONNX 算子线程数。同一 Python 服务进程中的模型实例可并行计算，每个实例独立加载模型和预热音色。增加实例会增加内存占用。

Compose 使用同一个 `M5_WORKERS` 同时设置推理实例数和 Go 并发；手动启动两个进程时必须自行保持一致，网关会核对推理服务声明的容量，不一致时返回未就绪。

## Docker 部署

准备好 INT8 模型目录后，从源码构建 M5 和网关。已有现场配置时将命令中的 `.env.m5.example` 换为实际的 `.env.m5`。

```powershell
docker compose --env-file .env.m5.example -f compose.m5.yaml up -d --build
```

生产部署先复制 `.env.m5.example` 到独立配置文件，例如 `.env.m5`，修改模型路径、音色和镜像前缀。镜像发布后设置：

```dotenv
TTS_IMAGE_PREFIX=ghcr.io/zqhhh77/faster-qwen3-tts
TTS_IMAGE_TAG=sha-完整提交SHA
```

然后：

```powershell
docker compose --env-file .env.m5 -f compose.m5.yaml pull
docker compose --env-file .env.m5 -f compose.m5.yaml up -d --no-build
docker compose --env-file .env.m5 -f compose.m5.yaml logs -f m5-backend gateway
```

仅 gateway 端口对外发布。gRPC 无鉴权，只用于受信的容器内部网络，不应直接映射到公网。一个 gateway 独占一个缓存目录。

## 测试和镜像构建

### 一键寻找 workers / threads 组合

调优入口是 `python -m backend.m5.tune`，默认模拟 6 个不同任务同时到达，通过 `--concurrency N` 可更换为任何 1～128 的并发数。它逐组启动独立的临时 gRPC 服务、加载并预热模型，再执行相同业务负载；每组结束后关闭自己的子进程，不修改或重启正在运行的服务。

例如在服务器的源码目录执行：

```bash
uv run --frozen python -m backend.m5.tune \
  --model /data/models/M5-TTS-50M-ONNX \
  --concurrency 6
```

使用镜像时可运行一次性容器，自动沿用 Compose 的模型、音色挂载和环境，无需在宿主机安装 Python：

```bash
docker compose --env-file .env.m5 -f compose.m5.yaml run --rm --no-deps \
  --entrypoint python -v "$PWD/m5-tune-results:/results" m5-backend \
  -m backend.m5.tune --concurrency 6 \
  --output "/results/run-$(date +%Y%m%d-%H%M%S)"
```

把 6 改为需要评估的并发数。测试会使用所在机器的 CPU/内存，现有业务负载也会影响结果，应在低峰或单独测试节点执行。不同候选组包含模型加载和预热，完整测试可能需要数分钟以上；进度、每组日志和已完成结果会持续写出。

默认识别可用逻辑 CPU、Linux affinity/cgroup CPU 配额，为 workers 选择一组覆盖少量实例到目标并发的候选，threads 按 CPU 预算选择。`workers × threads` 不超过预算，这只是筛选候选的启发式规则，并非进程全部 OS 线程数。需要更全面搜索或限制测试资源时可显式指定：

```bash
uv run --frozen python -m backend.m5.tune \
  --model /data/models/M5-TTS-50M-ONNX --concurrency 6 \
  --workers 1,2,3,4,5,6 --threads 1,2,3,4,6 \
  --cpu-budget 12 --max-memory-gb 8 --rounds 3
```

可先加 `--list` 查看候选，不加载模型。默认子进程 RSS 预算为测试开始时可用内存的 70%，也考虑常见 cgroup 内存限制；超过预算就终止当前测试子进程并排除该组。RSS 为采样统计，不能替代容器的硬内存限制。默认每任务超时 120 秒（设置了 TTS_TASK_TIMEOUT_SECONDS 时沿用环境值）、每组启动超时 600 秒，可用 `--request-timeout` 和 `--startup-timeout` 调整；任务时限应与正式网关一致。

默认提供少量中文示例，正式选型应传入接近真实业务长度的文本。`--texts /path/texts.txt` 接受 UTF-8 文件，一行一条，至少有 concurrency 条不同文本。同一句话使用不同音色也属于不同任务，可以改用 `--requests /path/requests.json`：

```json
[
  {"input": "前方船舶请注意安全。", "voice": "xiaoli"},
  {"input": "前方船舶请注意安全。", "voice": "xiaowang"},
  {"input": "请保持安全航速。", "voice": "xiaoli"}
]
```

JSON 数组至少包含 concurrency 项，每项支持 input、voice、language。省略音色会解析为真实默认音色，语言大小写也会统一；解析后重复的任务会被拒绝。简单文本模式可用 `--voices` 指定音色配置文件、`--voice` 选择音色，默认使用服务配置。

容器运行时这些文件参数使用容器内路径，例如把任务文件放在宿主机 `references/requests.json`，参数使用 `--requests /references/requests.json`。

每组会先让每个实例执行一次完整推理预热，再测默认 3 轮。请求同时提交，当 workers 少于 concurrency 时在客户端按实例数派发，并把排队时间纳入首块、完成延迟及任务超时。它直接调用 gRPC，不经过 HTTP/磁盘音频缓存，不会因为相同音频缓存命中而虚高；报告的是推理容量与派发等待，不包含 HTTP、网关磁盘和外部网络。

测试后端能否连续供音时，使用正式部署的模型和接近现场长度的告警文本。例如在仓库根目录测双路推理：

```bash
uv run --frozen python -m backend.m5.tune \
  --model models/M5-TTS-50M-ONNX-depth-int8 \
  --concurrency 2 --workers 2 --threads 3 --rounds 3 \
  --texts alerts.txt --require-continuous
```

`alerts.txt` 每行一条告警，本例需要两条不同文本。脚本按收到第一块 PCM 即以原速播放计算。每个后续音频块到达时，如果之前收到的样本已播完，就记录一次缓冲耗尽。首块等待、语音内部的自然停顿和最后一块之后等待完成标记的时间均不计入。该指标反映后端到 gRPC 客户端的供音连续性。

报告中每条成功请求和每组配置均列出 `underruns`（中断次数）、`stall_s`（累计中断秒数）和 `max_stall_s`（最长一次中断秒数）。组汇总另列 `stalled_requests`（出现中断的成功请求数）。加上 `--require-continuous` 后，只从正式测试请求全部成功且零中断的组中推荐配置；若无合格组，仍保存报告，进程返回 1。

输出独立结果目录，包含：

- `results.json`：每轮每个任务的数据、失败原因和推荐结果。
- `results.csv`：各组合的请求/秒、音频秒/秒、首块 P95、完成 P95、整批耗时、采样峰值 RSS 和启动耗时。
- `recommended.env`：全部测试完成后，从全部任务成功的候选中选择请求吞吐最高的一组；吞吐相同时优先首块 P95、再优先较低内存。不自动修改线上配置。

推荐文件包含 M5_WORKERS、M5_THREADS、TTS_MAX_CONCURRENT_TASKS，以及接纳本次并发所需的最小 TTS_MAX_PENDING_TASKS（concurrency 减 workers）。Compose 已自动关联推理并发，将 workers、threads 和等待队列配置写入部署文件，并根据业务要求检查 P95 是否可接受，再重新创建服务。网关的读者上限、磁盘缓存容量也需要足以接纳目标并发：当前每个未完成任务会预留最多 8 MiB 输出空间，调优脚本不测这部分容量。

此结果是当前候选、业务样本、并发数和机器负载下的最优，不是任意负载下的通用最优；单轮样本少时 P95 只是该样本的统计值。内存为整个测试进程树采样 RSS 之和，共享映射页可能重复计数。
